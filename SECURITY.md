# Security Policy

## Supported versions

Security fixes are released for the latest minor version of CcinnPsql.

| Version | Supported |
|---|---|
| 1.0.x | ✅ |

## Reporting a vulnerability

Please **do not open a public issue** for security problems.

Report vulnerabilities privately through GitHub's [private vulnerability reporting](https://github.com/whiteCcinn/ccinnpsql/security/advisories/new). Include:

- a description of the issue and its impact,
- steps to reproduce (PostgreSQL version, poolers, connection options, sample data if relevant),
- any suggested fix.

You can expect an acknowledgement within a few days. Once a fix is available, we will publish a release and an advisory crediting the reporter (unless you prefer to remain anonymous).

## Scope and design notes

- Passwords and SSH secrets are stored in the macOS Keychain; saved profiles on disk never contain them. Query history and the MCP audit log redact `PASSWORD '…'`, credential-like options and passwords inside connection strings, and are written with 0600 permissions.
- **TLS:** `sslmode` works like libpq's (`disable`, `prefer`, `require`, `verify-ca`, `verify-full`). The TLS handshake happens on the same socket after PostgreSQL's SSLRequest; bytes the server sends after its `S` answer are handed to TLS, never to the protocol parser (CVE-2021-23222 class). `prefer` silently continues unencrypted when the server has no TLS, exactly like libpq — the workspace header and the MCP `server_info` tool always show whether a connection is encrypted. Use `verify-full` against servers you do not control. `verify-ca` and `verify-full` check the chain against your CA file (or the system roots) with standard X.509 rules, and `verify-full` matches the host name the way libpq does (subjectAltName DNS names and IP addresses, a `*.` wildcard for one label, the common name only when there is no subjectAltName of that kind). Apple's web-PKI rules (maximum validity, required extended key usage) are not applied, so ordinary private-CA PostgreSQL certificates verify as they do with `psql`. TLS 1.2 is the minimum. Client certificates are not supported yet.
- **Authentication:** SCRAM-SHA-256 (the server's signature is verified before the login is accepted, so a server that does not know the password cannot impersonate the real one), MD5 and trust. Clear-text passwords are only sent when explicitly enabled for a connection. GSSAPI/SSPI/Kerberos and SCRAM channel binding (`-PLUS`) are not supported.
- **Cancellation** uses PostgreSQL's CancelRequest on a new connection to the same resolved address (encrypted when the session is). The next statement waits until a cancel has been delivered, so a late cancel never hits a later statement.
- **MCP read-only access** means *no data or schema changes*, enforced in layers:
  0. **The role is the real control.** No SQL-text check can stop a privileged role: any function, or SQL built at run time (`'CO' || 'PY …'`, `chr(67) || …`, `convert_from(decode('…', 'base64'), 'UTF8')`), can run `COPY … TO / FROM PROGRAM` or read and write server files, and a READ ONLY transaction does not block that. So before every read-only tool call, CcinnPsql checks the session in the call's own READ ONLY transaction: on the same connection and immediately before the statement for `run_query` and `explain_query`, and in a transaction of its own on the database the tool reads for every other tool. If the current user or the session user reaches, through any chain of memberships (INHERIT and SET ignored, so `NOINHERIT` and PostgreSQL 16's `WITH INHERIT FALSE, SET TRUE` count too), a superuser or `pg_execute_server_program` / `pg_read_server_files` / `pg_write_server_files` (server programs and files), or `pg_read_all_stats` / `pg_read_all_settings` / `pg_monitor` (every session's SQL, every setting such as a replication password in `primary_conninfo`), the call is refused unless the connection's **Allow AI read-only access on a privileged role** setting is on (off by default). The check also reads the database's encoding and its longest character (`pg_encoding_max_length`), failing closed, so the statement is checked again with that encoding's name rules immediately before it runs. It refuses a session whose effective search path (`current_schemas(true)`, read before the check pins its own) includes one of orafce's schemas (`dbms_sql`, `dbms_pipe`, `dbms_alert`, `utl_file`), under either setting: their functions have generic names (`open_cursor()`, `fopen()`), so an unqualified call would reach them past the text check; the search path is never rewritten. It also requires `client_encoding` to be UTF8 (the client sends it in the startup packet, which outranks `ALTER ROLE … SET client_encoding`), so the server reads the text with the same character boundaries as the guard. It runs with `search_path` pinned to `pg_catalog, pg_temp` and qualified names, and if it cannot run, the call is refused (fail closed). PgBouncer's admin console is not PostgreSQL and has no catalog to check; there only a single `SHOW` is sent.
     `SECURITY DEFINER` functions and procedures owned by such roles that the session may execute are **reported, not refused** (in every response's `security_notices`, on errors too after the message, and in Settings → MCP → Check Role, for every schema of the database the call uses). Extension-installed functions will often appear in the list. The check can't see inside them, so they remain an **accepted risk**: a plain role can reach a privileged action through one of them.
     Foreign tables the session may read (any column) whose table, server or wrapper options include `program` or `filename` (file_fdw, or any wrapper with such options) are reported the same way: reading one runs the program, or reads the server file, that its creator chose, as the server's operating-system user, and nothing in the SQL text shows it. They remain an accepted risk too. A wrapper that runs commands under other option names is not detected. Readable foreign tables of other wrappers (postgres_fdw, …) are listed as well (a fixed remote destination, informational).
     Functions and procedures in untrusted languages (`NOT lanpltrusted`: internal, C, plpython3u, plperlu, …) that the session may execute, outside `pg_catalog`, `information_schema` and the members of a reviewed extension list (plpgsql, pg_trgm, btree_gin, btree_gist, citext, hstore, cube, earthdistance, fuzzystrmatch, intarray, isn, ltree, seg, unaccent, uuid-ossp, pgcrypto, vector, postgis, postgis_raster, postgis_topology; deliberately not pg_stat_statements, pageinspect, pgstattuple, pg_buffercache, dblink, postgres_fdw, file_fdw, tablefunc, adminpack, pg_net or http), are reported the same way: a superuser's `CREATE FUNCTION … LANGUAGE internal AS 'pg_read_file_all'` is executable by PUBLIC by default and reads server files as any role. Calls to them by name are also refused, but that is **best effort**: views, operators, casts, column defaults and row security call functions implicitly. The real control is a role without EXECUTE on them. Aggregates and range-type constructors (language internal, nothing of their own) are not listed. Functions in `pg_catalog` are not listed either, so an unreviewed extension a superuser installs into `pg_catalog` escapes the listing. An integration test requires every extension the tested images ship to be reviewed or listed as not reviewed.
  1. The app's PostgreSQL lexer accepts only a single read (`SELECT`, `WITH … SELECT`, `VALUES`, `TABLE`, `SHOW`, `EXPLAIN` of those) and rejects writes, data-modifying CTEs, `SELECT … INTO`, `COPY`, `DO`, `CALL`, transaction control, `SET`, row locks, Unicode-escaped identifiers and `UESCAPE` (one lexical check that every statement path and every literal's content runs, so `SHOW U&"app\002ejwt_secret"` is refused like a `SELECT`), names (unquoted, keywords or quoted) holding one of the 19 letters whose upper, lower or title case contains an ASCII letter (`ß İ ı ŉ ſ ǰ ẖ ẗ ẘ ẙ ẚ K ﬀ–ﬆ`, derived from Unicode's case mappings by a unit test; a Turkish-locale LATIN5 or WIN1254 database lower-cases `PG_SETTİNGS` to `pg_settings` and `pg_termİnate_backend` to `pg_terminate_backend`), and — once the role check has read the database's encoding — any unquoted name or keyword with a non-ASCII letter in a single-byte database (LATIN*, WIN125*, SQL_ASCII, …), where the server folds high-bit bytes with the locale's `tolower()`, which no client can model (quoted names are exact; UTF-8 and other multi-byte encodings never fold non-ASCII letters), functions with side effects (`pg_terminate_backend`, `set_config`, `pg_notify`, advisory locks, large objects, server file access, replication slots, `dblink`, …), writes a READ ONLY transaction does not stop (`brin_summarize_new_values`, `brin_summarize_range`, `brin_desummarize_range`, `gin_clean_pending_list`, pg_surgery's `heap_force_*`, pg_visibility's `pg_truncate_visibility_map`) and state that outlives the transaction (`setseed`, `pg_nextoid`, …), and the known functions that run SQL passed as text (`ts_stat`, `ts_rewrite`, `query_to_xml`, `cursor_to_xml`, `crosstab`, `connectby`, pgRouting `pgr_*`, Citus `run_command_on_*`, `pg_background_*`, pgTAP's `lives_ok` / `throws_ok` / `results_eq` / `set_eq` / `bag_eq` / `is_empty` / `row_eq` / `performs_ok` / `runtests` and its runners, orafce's `dbms_sql.*` together with `dbms_pipe`, `dbms_alert` and `utl_file`, `hypopg_create_index`), and network requests (pg_net's schema `net`, also on the search path; pgsql-http's `http`, `http_get`, `http_post`, …). Other extensions may ship more such functions; only the role check (layer 0) and the server's privileges bound those. An integration test requires every VOLATILE core function to be forbidden or on a reviewed list of harmless ones, on each tested version. Where readers could disagree, it takes every reading: a statement is allowed only if it passes as PostgreSQL 13–14 read it (`1.5into t` is `1.5 INTO t`), as 16+ read it (`0x1F`, `1_000`, trailing junk) and with keywords matched under any case mapping (`ınto`). It refuses direct reads of the views, tables and functions that show other sessions' SQL text, connection strings, credentials or configuration secrets: `pg_stat_activity` and `pg_stat_get_*activity`, every `pg_stat_statements*`, `pg_authid`, `pg_shadow`, `pg_user_mapping(s)`, `pg_subscription`, `pg_stat_wal_receiver`, `pg_stat_replication`, `pg_foreign_server` / `_data_wrapper` / `_table` options, `pg_largeobject`, `pg_file_settings`, `pg_hba_file_rules`, `pg_ident_file_mappings`, `pg_current_logfile()`, and the extension views of other sessions' SQL (`pg_stat_monitor*`, `pg_store_plans*`, `pg_qualstats*`, `pg_stat_kcache*`, `pg_show_plans`, pgsentinel's `pg_active_session_history`, PoWA's `powa_*`), besides the forbidden file, large-object and dblink functions. Role and database settings can hold secrets (`ALTER ROLE app SET myapp.api_key = '…'`), so it refuses `pg_db_role_setting`, the `rolconfig` / `useconfig` columns and the catalogs whose rows include them (`pg_roles`, `pg_user`: `SELECT *` or a whole-row reference shows them), `pg_settings`, `pg_show_all_settings()`, `SHOW ALL`, and a lookup of a custom parameter (every custom name has a dot): `SHOW` takes exactly one plain, unquoted ASCII name other than `ALL` (every built-in parameter is one; quoted, escaped and dotted names can spell a dot or `ALL`), and `current_setting()` one literal, built-in parameter name. Two tools give the AI what those refusals take away, by fixed columns with an allowlist on top: `get_settings` returns built-in parameters only (name, setting, unit, category, description, source, pending restart; never a dotted name, `sourcefile` or `sourceline`, and its name filter is matched in the app, not sent as SQL), and `list_roles` returns role names, attributes (`rolinherit` included), connection limits and memberships (never `rolconfig`, `rolpassword`, `rolvaliduntil` or role comments); both go through the role check like every tool. A function that reads a setting by a name it builds at run time (one already in the database, or an extension's) remains possible. Because a name list cannot see a relation or SQL chosen at run time (`table_to_xml(c.oid::regclass, …)` with the name built from strings), every built-in that reads a relation or runs SQL given at run time is forbidden: the `table_to_xml`, `schema_to_xml`, `database_to_xml`, `query_to_xml` and `cursor_to_xml` families (with their `_xmlschema` and `_and_xmlschema` forms), `ts_stat` and `ts_rewrite` at any arity, and the statistics writers `pg_clear_*` / `pg_restore_*`; an integration test enumerates such core functions on each tested version. The list is security-critical: an integration test enumerates every pg_catalog view, table and function with a `query`, `conninfo`, `password`, `options`, `config` or `setting` result column on each tested version, and requires each to be refused or proven harmless (storage options of `pg_class`, `pg_attribute`, `pg_tablespace`; a function's own SET clauses in `pg_proc`; `pg_extension`'s configuration-table list; `pg_config`'s build settings). `get_activity` and `get_top_statements` return other sessions' SQL with every string and numeric literal replaced by `?` and comments removed (both readings of `standard_conforming_strings`), not only credentials. A NUL character anywhere (the transport refuses to send one rather than strip it), a `;` anywhere in the statement, `BEGIN ATOMIC`, `TO PROGRAM` / `FROM PROGRAM` (also inside literals), a nested block comment, or a backslash before a quote in a `'…'` string (which ends it early when `standard_conforming_strings` is off) is refused.
  2. Because a list of SQL-taking functions always misses one (any function that does `EXECUTE`), the content of every string literal — plain, `E''` and `U&''` with their escapes decoded, dollar-quoted, with continued literals joined — is read as SQL again: content in which any statement starts with a verb (also after a leading `;` or `(`) must itself pass the whole check, which takes one statement only (up to four levels deep), and no content may call a forbidden function. This is conservative by design: text that merely looks like a write (`'delete'`) is refused.
  3. Every tool argument other than `sql` (connection, database, schema, table, filters) is refused, before anything is sent, when it holds a control character (Unicode Cc: NUL, C0, DEL, C1); names reach the server as given, and neither the startup packet nor identifier and literal quoting ever changes one (a NUL is refused by the transport, never dropped). The guard checks exactly the text that is sent, after every rewrite (`run_query`'s automatic LIMIT, `explain_query`'s EXPLAIN prefix). The statement runs through the extended protocol (one statement per message; on a PgBouncer admin console, which only takes the simple protocol, exactly one `SHOW`) inside `BEGIN TRANSACTION READ ONLY … ROLLBACK` with a statement timeout and `standard_conforming_strings` pinned on, so the server reads string literals exactly as the lexer did.
  4. After every MCP call the session is reset before the pooled connection is reused: `DISCARD ALL`, or behind a transaction pooler `SELECT pg_advisory_unlock_all(); UNLISTEN *; RESET ALL` (no `DISCARD ALL`/`DEALLOCATE ALL`, which would drop the pooler's own prepared statements). A connection that cannot be reset is closed. So a session advisory lock, a prepared statement or a setting created by SQL built at run time cannot outlive the call.

  **Residual risk:** a side effect inside a function that already exists in the database (for example a `SECURITY DEFINER` function that calls `pg_terminate_backend`), or SQL assembled at run time and handed to such a function, cannot be recognised lexically, and a READ ONLY transaction does not stop non-write side effects; on a role that is not privileged (layer 0), the server's own permissions still apply. For real isolation give the AI connection a dedicated low-privilege role, for example `CREATE ROLE ai_reader LOGIN PASSWORD '…'; GRANT pg_read_all_data TO ai_reader;` on PostgreSQL 14+ (the Settings → MCP pane shows this). Issues that let a read-only MCP connection change data or schema, or have effects through built-in functionality, are considered vulnerabilities.
- SSH tunnels use the system `/usr/bin/ssh` with `StrictHostKeyChecking=accept-new`: changed host keys are rejected. They use `ControlMaster=no` and `ControlPath=none`, so a tunnel neither becomes nor joins a shared connection master: it always authenticates with the profile's credentials, and its forwarded port closes with it. Your own ssh sessions keep their masters. Known limitation: these options apply to the ssh the app starts; with `ProxyJump` (or a `ProxyCommand` running ssh) in `~/.ssh/config`, the jump connection is made by a child ssh that reads your config and may still use or become a shared master. Secrets reach ssh through a short-lived 0600 file, never through the environment or command line.
- Statements built by the app (metadata, cancel/terminate, materialized-view refresh, LISTEN/NOTIFY) use bound parameters or quote identifiers and literals; issues that allow injecting SQL through object names are considered vulnerabilities.
- Update checks contact only `api.github.com` and `github.com`, send no personal data (the User-Agent is `CcinnPsql/<version>`), and run at most once a day unless you check manually. A downloaded disk image is accepted only from this repository's download URL for the same release tag, at the size the release lists, and with the SHA-256 published in that release's `SHA256SUMS.txt`. The checksum guards against corruption and truncation, not against a compromised GitHub release; authenticity relies on HTTPS to github.com. The app never replaces itself; you drag the new version into Applications.
